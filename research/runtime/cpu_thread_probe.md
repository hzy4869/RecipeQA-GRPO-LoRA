# CPU线程数对固定四图输入编码的影响

日期：2026-11-05。目的：检查容器12 CPU quota环境下默认72个Torch线程是否造成前处理过度订阅。只读探针经现有SSH master运行，未改env.sh、冻结源码、数据、模型或正式进程；未启动GPU任务。

## 条件和比较方法

- 远端项目：`/root/autodl-tmp/rl_recipeqa`，读取原`env.sh`及同一`.venv`。
- 子进程设置`CUDA_VISIBLE_DEVICES=''`，初始`torch.get_num_threads()`实测为72。探针仅调用`torch.set_num_threads`改变自己的线程数。
- Processor：实际本地`Qwen3-VL-2B-Instruct` snapshot，revision `89644892e4d85e24eaac8bacfd4f463576704203`；使用冻结`InputConfig`，每图min/max pixels为65,536/262,144，食谱token预算1,536，输入上限4,096。
- 从冻结`data/manifests/debug.jsonl`读取前8题。先在4线程下用真实`prepare_record`得到每题统一裁剪后的prompt，并用`load_images`解码RGB；三个条件复用完全相同的prompt和PIL图片。
- 先做一次不计时warm-up编码。正式条件按 **4线程→72线程→4线程复测** 顺序，每条件8题；逐题计时真实`encode_messages`，包含chat template、tokenizer与四图processor，计时不包含结果clone及比较。
- 对每个编码输出的全部Tensor检查key集合、shape、dtype，以及`contiguous().view(-1).view(torch.uint8)`后的原始字节。第二/第三条件均与第一条件逐题比较，包括pixel values、input IDs、mask及image grid等实际输出键；不以“预测结果看起来一样”替代输入检查。
- 正式SFT前处理当时在另一进程并发运行，因此绝对耗时受CPU竞争和缓存影响。此探针测输入编码，未测GPU训练吞吐，也未声称所有2,048题均已逐字节交叉核验。

## 处置边界

证据支持主执行者在首个正式更新前统一降低CPU线程数，并保留原预处理attempt、记录新资源配置。实际是否设置OMP/MKL线程、是否重启及何时重启均由主执行者决定，本探针没有执行这些动作。后续三主分支应统一资源设置并报告真实成本，不因此改动模型、像素预算、奖励或开发选择规则。
