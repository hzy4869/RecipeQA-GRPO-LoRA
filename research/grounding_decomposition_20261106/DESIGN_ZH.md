## 1. 最清楚、可被否证的研究问题

**在同一输入下，排序模型能否将每张照片定位到食谱的可见步骤；如果把正确对应关系直接交给它，排序/标签输出还会失败吗？** 更进一步，模型写出的对应关系与它最终给出的顺序是否一致？

这里必须区分三件事：绝对步骤定位、足以支持排序的相对先后、按已知数字对应关系组合输出标签。绝对步骤号错了，不一定导致相对排序错；模型解释的步骤号也不一定就是它在原 answer-only 提示中实际使用的内部依据。这个诊断测的是可观察的匹配、组合和提示干预效应，**不声称恢复隐藏思维链或把原错误因果归到唯一内部模块**。

建议先固定原 `flow44/raw_sft/checkpoint-64`，不根据当前 FWD 结果挑模型。单模型先把测量做干净；若要研究“RL改变哪一环”，另行在相同32题上预先冻结配对的原 `exact_kl/checkpoint-64` 和/或 FWD64，不能事后只加表现最好的一个。只有单个模型的分解不能解释RL与SFT的差异。

## 2. 免费标签实际是什么

代码证据：

- `src/recipeqa/data.py:72` 的 `source_image_step()` 从数据文件名中的步骤字段提取来源步骤；`canonicalize_row()` 同时核验四张图对应四个不同、递增且存在于全文的 source step，四个原候选含相同图片集合。
- manifest已有 `steps[*].source_step_id`、`source_step_ids_chronological`、`display_perm`、`target_order`、`target_labels` 和实际图片路径。无需新人工标注，就能得到“显示标签A–D对应哪个来源步骤”的**数据集来源标签**。
- `src/recipeqa/modeling.py:404` 的 `_render_recipe()` 按 `enumerate(steps,1)` 输出 `Step 1, Step 2, ...`；原 `source_step_id` 不进入可见文本。
- `src/recipeqa/process_metrics.py:82` 的 `gold_display_steps()` 已正确实现 source ID→实际1-based可见编号→显示位置的转换，可以复用其边界校验思想/函数。

精确映射为：先做 `visible[source_id] = context_index+1`；再对显示位置p，取语义图片身份 `s=display_perm[p]`，金标为 `visible[source_step_ids_chronological[s]]`。**不能简单比较预测数字与source ID，也不能普遍假定 source ID+1。** 例如本固定队列第1题四个来源步骤是 `[1,5,6,8]`、display `[3,2,1,0]`，因此显示A/B/C/D的正确可见步骤是 `[8,6,5,1]`，排序为D C B A；这些backend数字/文件名不得进入普通或匹配提示。

此标签来自资料归属，不等于人类已核实的唯一视觉语义。照片可能展现多个动作、上一动作的结果，或与相邻步骤同样相符；所以报告应称“与来源步骤一致率”，不能无条件称“真实感知准确率”。原人工审核仍pending，不能自动生成“图片清晰”“步骤唯一”的人类判定。

## 3. 固定32题的CPU核查结果

来源：原 `data/manifests/val.jsonl`，SHA `c998796fbc07a24c7a24062d6d0aba07500c75b34568fd7ba67f8c38daae03c9`，前32条、32个不同食谱、128张目标照片。完整逐题元数据见 `KNOWN_DEV_METADATA_AUDIT.json`，只用于定义/审计，不按答题分数筛选。

- 可见食谱步骤数最小4、中位6、最大14。不能只给4个金标步骤让模型匹配，否则删掉了真实干扰项。
- 这32题的context source ID目前均从1开始且连续，可见编号恰好与source ID相等；没有实际发现off-by-one。仍保留通用映射与round-trip检查，不能把“潜在编号风险”写成已发现的数据错误。
- 32题的四张目标图均来自4个不同步骤，无来源步骤并列。数据封装本来就拒绝同一步抽两图；未来若扩展为同一步多图，必须转为允许并列的偏序问题，不能用标签字母或显示顺序打破平局冒充金标。
- 原SFT64输入审计显示3/32题食谱正文被均匀截短，而且这3题均至少有1个目标步骤正文被截短。所有步骤标题仍保留，步骤没有被删。其余29题作为预先定义的“无正文裁剪”描述性分层；不删去3题，只同时报告全32与29/3分层。
- 原A输入token范围663–2014（4096上限），recipe token最多1535（1536上限）。追加短的匹配格式应有余量，但须在未来真实processor CPU预检中逐题证明，不能凭估计改变截断策略。

视觉封装先按原图读入RGB，再用固定65536–262144像素processor resize；当前封装没有按金标手工选区域。不能把分辨率导致的信息损失与文字截短混为一谈。本诊断必须保持四图字节、显示顺序、像素预算、grid及实际预处理不变，不借机裁出更清楚的目标。

## 4. 最小实验矩阵：32次新多模态推理即可取得核心分解

| 条件 | 输入与输出 | 新调用 | 目的 |
|---|---|---:|---|
| A：原任务 | 原完整食谱、四图、原answer-only提示；只输出排序 | 0，可复用已有32条 | 原任务对照，不补看test、不挑错题 |
| B：显式匹配+排序 | 与A完全相同的可见食谱和四图；输出四个可见步骤号及最终排序 | 32次多模态 | 同时测来源匹配、相对次序和自洽性 |
| C：正确对应表→排序 | 只给A–D对应的正确步骤号，不给图片或食谱；只输出排序 | 32次短文本 | 检查已知匹配后的数字组合/标签输出能力；**oracle非部署分数** |
| Cπ：反事实对应表 | 在同一32题上固定循环置换表中的对应关系；对新表计算独立答案 | 32次短文本 | 检查是否真正遵循输入表；不能拿原图片金标给Cπ判分 |

**核心新增32次多模态+64次短文本，共96条。** Cπ是便宜而有力的控制，建议保留；若只做最小可用版，B+C共64条，但其表格遵循检验较弱。C、Cπ只测数值组合，不叫“多模态准确率提升”，不能混入A/B的分数、也不能用oracle生成训练样本后把它当纯RL收益。

B不必生成长篇解释或视觉描述，建议严格五行：

```
A: step <可见编号或unclear>
B: step <可见编号或unclear>
C: step <可见编号或unclear>
D: step <可见编号或unclear>
Order: <四个标签>
```

四个数字可相同，不能在生成时强制选不同步骤；重复本身是待观察的定位失败。使用全部context步骤，不透露哪4步有目标图。提示中只出现模型原本可见的Step编号，不出现qID、source ID、图片文件名、来源步骤或金标。B的中间数字是模型新输出，不能塞入正确值。

C/Cπ将表声明为权威输入，例如 `A:8, B:6, C:5, D:1. Return labels in increasing numerical step order.`；Cπ把这张表循环替换为 `A:6, B:5, C:1, D:8`，新答案为C B A D。**Cπ的正确答案是新表的排序，并非原图片的D C B A。** 这可以否证“只是继续输出熟悉标签顺序”的解释。

不建议第一轮直接为四张图各开一次调用：那将B从32增为128次，且单图上下文与原四图任务不同。若B显示明显标签/互相干扰，再另立单图条件；不应先建复杂trainer。

## 5. 需要哪些指标，哪些结论不能偷换

每题保存B的四个原始数字/unclear、严格格式状态、最终Order、独立CPU导出排序以及A原回复。分别报告：

1. **来源步骤一致**：128张图的匹配比例、32题四图全匹配率；missing/unclear/out-of-range在固定分母中计错，技术失败另列并使覆盖不完整。
2. **足以支持排序的相对匹配**：从B预测步骤号计算6对先后，ties计该对错误；报192对固定分母及32题严格可排序覆盖率。所有4数有效且不同才生成完整CPU排序；不以标签字母或输入顺序打破模型自己制造的tie。
3. **B最终排序**：与原金标比较Exact/Pair，同时与A比较。格式不完整与最终Order有效性独立报告，不能只统计解析成功子集。
4. **B自洽性**：在完整、有效、不同编号时，最终Order是否等于其自身步骤号的确定性排序；报告可比较覆盖数及全32固定分母，而不是只给漂亮的条件率。
5. **Oracle组合**：C与Cπ各自32题的排序Exact/有效率、对表循环变化的响应一致性。全部32×2均保存，不能按C是否正确选择Cπ题。

特别重要：**“四个金标步骤→CPU sort得到100%”只是标签映射单元检查，不是模型成绩或insight。** “四步完全匹配→CPU排序必正确”也是数学蕴涵，不能当研究发现。真正值得看的，是模型B何时在绝对步骤、相对次序和最终答案之间分离，以及给定正确表之后C仍会不会错。

可以被数据反驳的情形：

| 观察 | 能支持什么 | 不能声称什么 |
|---|---|---|
| B绝对步骤号经常错，但相对次序及排序仍对 | 精确步骤定位比任务需要更严格；“步骤号低分”不等于排序推理差 | 不能据此宣称感知模块整体失败 |
| B四步均匹配，但最终Order错；C/Cπ对 | 匹配提示下有可观察的组合/输出不自洽 | 不能直接解释A的隐藏推理路径 |
| B推导次序错、最终也错，而C/Cπ高 | 图像/食谱对应是一个值得进一步干预的候选瓶颈 | 不能排除提示改变、来源标签歧义、文本缺失或视觉分辨率因素 |
| B比A好 | 显式分解提示改变了行为，可作提示方法的探索结果 | 不是训练改进或RL增益；额外输出/计算须记账 |
| C或Cπ也错/无效 | 连给定对应表后的组合/协议执行都不稳定 | 不能把所有原错误归因于视觉感知 |
| B、A答对，但B对应错/自洽性低 | 解释/对应输出与最终答案可能分离，值得警惕解释性指标 | 不能断言模型在“故意撒谎”或还原真实CoT |

如果之后固定比较SFT/EK/FWD，只有在相同B/C提示、数据、token预算和解码下看到稳定差值，才能说RL改变了这些**显式可观测行为**。单个seed或32题不是普适因果证据。

## 6. 防止裁剪和提示变化成为隐性混淆

不能独立调用 `prepare_record(process=True)` 后直接假定它与A拿到相同正文：原函数会按当前完整提示的input上限重新二分正文cap。正确做法是先用A的既有 `uniform_body_cap` 与原tokenizer重建**确切可见recipe文本**，核验其渲染hash/文本与A一致，再为B替换任务中的“只输出四个标签”限制并使用五行输出指令，不能留下两套互相冲突的格式要求；四图、标题和recipe文本不变。B的实际encoded长度必须≤4096，不能为B静默再次截正文、丢标题或删图。

这32题A最多2014 input tokens，有超过2000 token余量，因此短B应该能容纳；未来仍要逐条真实CPU编码确认。如果任何B超上限，暂停并明确新共同输入政策；若为A/B另定共同cap，则必须重跑A，不能继续用旧A当同输入对照。

C/Cπ明确是oracle文字条件，刻意改变输入信息，不与A声称等计算或同任务。B新增token/生成预算亦须单列：建议greedy、max_new_tokens64（不是A的32），因为五行格式确实更长；比较时报告完成token及触顶率，不能将长输出截断误称定位错误。CPU预检应确认合法五行模板本身能在64token内完成；运行中触顶是需保留的模型行为（单独标记，并留在固定分母），不能因为答得冗长/低分就逐题加token或重试。只有明确的编码/协议技术缺陷才可保留失败版本并另锁修订。

- 固定数据和免费金标：既有dev200前32条及 `gold_display_steps()`；`KNOWN_DEV_METADATA_AUDIT.json`已固定qid、来源→可见映射、裁剪情况，没有读取答题分数来选人/选题。
- 原A：`exploratory/principled_ordering_20261105/finite_trials_v2/flow44/raw_sft/dev64/predictions.jsonl` 及config，已有同一固定模型、相同32题原prompt回复和实际input_audit。可按qid/presentation严格join，验证model bytes/输入/解码身份后重算分数，无新GPU。
- 通用代码：冻结的图像/文本输入、覆盖验收、raw writer、模型identity与数据盘检查思路；新B格式应使用新小parser，不修改原 E4 parser 或把不存在的观察文本填成假证据。
- 已有val过程校准5题：来源是monitor前5、模型为旧W checkpoint16，与本32题重合0，不能拿来当本固定模型的B结果。只可借用既有格式/编号校验经验。
- 旧E4 main/process40来自原test体系，**本任务没有读取其成绩或内容，也不把它用于当前开发选题或配对诊断**。原人审pending的事实不变。
- 旧完整展示orbit16×24可以说明标签展示行为，但不含图→步骤预测，不能凭既有排序raw反推出模型“认为A是第几步”。

## 8. 时间成本与执行前门槛

固定SFT64既有前32题A的实际5-token生成耗时：合计11.39秒，中位每题0.322秒，最大1.188秒；这只包含生成，不含加载/预处理，不能直接当新五行任务的总时长。

单模型推荐新增B32（≤64生成token）+C32/Cπ32（各≤32短文本token），粗略预计**3–10分钟推理及编码，预先设15分钟硬上限，约0.4元GPU租时**。是基于旧吞吐和更长输出的工程估计，尚无真实新prompt计时；需固定前2题pilot后按整批96条作保守时间gate。若额外重跑A32，通常再加几十秒到数分钟，仍单列成本。增加第二个预先选定模型大致将新增调用/生成翻倍，需另冻结预算，不是本草案的运行授权。

实现/核验/分析预计需要约3–5个集中人时：新短格式runner与CPU映射/解析检查约1–2小时，输入同一性/工件复用和小批验收约1小时，32题逐类汇总及案例核对约1–2小时；不需要下载新数据或搭建新trainer。若要求两位成员做全部128图语义唯一性人工审核，会另增加人时，当前没有假定这项审核已有人完成。

进入执行前应另锁：32题qid/model bytes；A/B可见文本和图片身份；B/C/Cπ模板、输出token、parser、反事实循环政策；固定分母；时间/成本/排它锁/失败不续跑政策；原raw、metadata、完整结果和全部负例工件。不打开确认集；不由诊断直接改奖励或制造新训练预算。

**下一步的价值是先把“哪个可观察环节出了问题”问清楚，再决定是否值得训练新的图文对齐目标。当前仅有标签和可检验方案，尚无任何新的匹配/排序分解结果。**
