# Coordinator implementation, local preparation only

The coordinator, draft builder, launcher, CPU preflight and focused tests are new files in this namespace. They do not modify or invoke the old coordinator. They retain the reviewed structure of the coverage coordinator (exclusive locks, fixed child queue, immutable dependencies, synchronous inherited process group and failure preservation), with an explicit new eight-arm contract.

`build_draft_policy.py` creates four fixed manifests and eighteen unexecutable child policies. The four formal/smoke manifests contain 256/4 unique records; repeated visits are represented by the child two-pass contract, never duplicated q0 cache rows. Initial SFT768 actual exposure is verified before preparation. The existing genuine 1024-reference cache is the only q0 source. No first-preflight clock is created here.

`command_schedule()` fixes 74 distinct commands: CPU 1, q0-only audits 4, ten technical runs plus their independent audits 20, eight formal runs with independent audit, dev prediction/coverage and orbit prediction/coverage 48, and the final complete-stage independent CPU audit 1. All ten technical audits and the complete time/storage gate precede the first formal call. Every run has a fresh persisted authorization binding parent/child hashes, the original clock, actual CPU receipt and all four q0 audits; formal authorizations additionally bind all ten technical audits and the whole gate. Every child is sequential and inherits the actual GNUtimeout parent's process group.

The coordinator consumes raw training timings and independent pass/fail receipts for admission. It reads prediction configuration and coverage reports to enforce completeness. It does not rescore predictions, read candidate performance for method choice, or issue scientific effect estimates. After the first73 successful commands it writes `science_completion.json`, which explicitly remains pending the global guard. Command74 executes `verify_refresh_run.py --stage-only` under the original clock/native watchdog. A one-byte pipe barrier permits the same PID to exec the verifier only after its actual child PID/PGID are persisted; an EOF or wrong release cannot enter the guard. The verifier accepts only that precise self-live slot or a later complete74 journal. Its success is bound by file SHA before `completed_eight_reference_refresh_endpoints_independently_verified` is committed. Subsequent statistical report preparation remains separate from this complete-stage integrity gate.

Resource accounting uses the slower of actual technical measurements and complete historical same-family runs. Training floors use all 256 updates' external wall time, rather than one hot step. It includes eight 128-update trainings, model/checkpoint overhead, two actual 256-row reference refreshes, eight 256-row final banks, 4672 greedy/orbit responses, sixteen prediction model loads, eight independent run audits, a 1.5 multiplier and 600-second margin. The common 20-hour clock starts before actual CPU work; a failed timing gate cannot shrink the queue or extend the deadline.

Initial disk admission includes 16 formal and 12 technical checkpoints, eight actual optimizer/gradient continuity snapshots, 512 MiB metadata/prediction reserve, 20% size variation and 1 GiB free margin. No redundant final-adapter export is expected. Once all technical artifacts are already stored, the formal gate checks the remaining sixteen formal checkpoints/four formal snapshots against current free space; it never deletes or discounts existing failed branches. The continuity-file bound is at least prior full-checkpoint plus adapter bytes, increased by actual technical measurements.

The focused suite currently contains 17 CPU tests covering missing arms/path smokes, exact command order, fixed endpoint/budget/test restrictions, source closure, historical timing completeness, slow technical paths, full storage counts, science/global completion separation and a real CPU-only same-PID/PGID pipe barrier. Every technical run must physically change its adapter and have a positive actual parameter update on every technical step; this admission condition never stops a formal arm for a negative/no-update scientific result. Local tests do not constitute remote CPU/native cleanup, actual smoke or resource admission. No SSH, GPU, model or optimizer calls were made to prepare these files.
